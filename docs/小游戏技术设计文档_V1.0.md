# 连连看小游戏技术设计文档 V1.0

> 文档状态：可用于第一阶段开发  
> 日期：2026-10-28  
> 核心目标：构建一套可被「快爽」「清理解压」「剧情换皮」三类产品共同复用的连连看游戏底座，并以最低边际成本持续扩展内容和产品形态。

---

## 0. 文档结论

第一阶段采用：

**一个代码仓库 + 一个 Cocos Creator 工程 + 一套 Link Core + 三个 Mode + 多套 Content Pack + 多产品构建配置。**

三类产品不分别开发三套连连看。

统一结构为：

```text
Link Core
├── Rule Core    规则正确
└── Feel Core    操作够爽
        │
        ▼
Mode Layer
├── Arcade       快爽
├── Clean        清理解压
└── Story        剧情换皮
        │
        ▼
Content Layer
├── 具体关卡
├── 具体场景
├── 具体剧情
└── 具体素材
```

核心设计原则：

> 三种产品共享相同的连连看基础品质，差异主要发生在「消除之外」。

快爽产品强调高频打击、Combo、挑战与单位时间爽感密度。

清理产品强调场景从脏乱到整洁的恢复过程。它可以整体节奏更舒缓，但单次点击、连接、命中、消除必须依然快速、干脆。

剧情产品强调剧情推进、角色、装修或轻经营。连连看承担节奏转换、参与感和奖励触发器的作用，不应成为阻碍玩家看剧情的高门槛关卡。

---

# 1. 项目目标

## 1.1 第一阶段目标

V1 要解决五件事：

1. 建立稳定、可测试、可复用的连连看规则内核。
2. 建立统一的操作手感与强反馈系统。
3. 支持快爽、清理、剧情三类 Mode 复用同一套 Link Core。
4. 关卡、反馈参数和大部分内容数据配置化。
5. 支持同一个工程构建出不同产品变体。

V1 的成功标准不是“做出完整商业游戏”，而是：

> 能用同一套核心代码快速做出三种明显不同的产品体验，并证明基础连连看本身足够爽。

---

## 1.2 产品级目标

### 快爽产品

核心情绪：

```text
快 → 准 → 爆 → 连 → 更快
```

重点：

- 输入响应快
- 连线反馈快
- 消除反馈强
- Combo 连续升级
- 失败/重开成本低
- 单局短
- 重复游玩意愿高

### 清理解压产品

核心情绪：

```text
脏乱 → 清理 → 恢复 → 完成
```

重点：

- 连连看操作仍然快
- 整体节奏允许慢
- 强调清洁进度
- 强调阶段变化
- 强调 Before / After
- 强调完成感，而非高难挑战

### 剧情产品

核心情绪：

```text
剧情悬念 → 参与 → 奖励 → 下一段剧情
```

重点：

- 关卡短
- 难度低阻力
- 剧情推进快
- 内容替换成本低
- 人物、背景、文本、装修物等高度配置化

---

# 2. 非目标与架构边界

## 2.1 V1 明确不做

V1 不建设以下系统：

- 万能游戏引擎
- 可视化关卡编辑器
- 自研脚本语言 / DSL
- 自研热更新框架
- 大型 ECS
- 通用剧情编辑器
- 通用商业化后台
- 通用运营后台
- 完整实时后端
- MMO 式账号体系
- 跨产品复杂社交关系
- 为“以后可能会用”而开发的抽象层

原则：

```text
三个产品都会用 → Core

两个以上产品明确会用 → Framework / Shared

只有一个产品使用 → Mode

仅仅“以后可能会用” → 现在不开发
```

---

## 2.2 Link Core 的边界

Link Core 只负责：

```text
“玩家如何完成一次高质量的连连看交互。”
```

它不知道：

- 当前是不是在清理鸡圈
- 当前剧情人物是谁
- 当前章节是什么
- 玩家有没有装修房子
- 玩家为什么获得金币
- 玩家有没有看广告

Link Core 可以产生事件：

```text
MatchSucceeded
PairRemoved
BoardCleared
ComboChanged
```

外部 Mode 根据这些事件决定业务含义。

例如：

```text
PairRemoved
    │
    ├── ArcadeMode → Combo + Score
    ├── CleanMode  → CleanProgress +2%
    └── StoryMode  → ObjectiveProgress +1
```

# 3. 总体设计理念

## 3.1 Rule Core 与 Feel Core 同等重要

基础连连看拆成两个核心域：

```text
LinkGameCore
├── RuleCore
└── FeelCore
```

### Rule Core

解决：

> 游戏规则是否正确。

负责：

- 棋盘
- 棋子
- 匹配
- 连线路径
- 消除
- 洗牌
- 提示
- 死局
- 棋盘生成
- 关卡目标的基础事件

### Feel Core

解决：

> 游戏是否“啪一下很爽，还想再点一次”。

负责：

- 点击反馈
- 选中反馈
- 连线表现
- 命中反馈
- Hit Stop
- Squash / Stretch
- 破碎动画
- 粒子
- 屏幕微震
- 音效
- 手机震动
- Combo 节奏反馈

---

## 3.2 “逻辑立即结算，表现异步播放”

这是 V1 的关键技术规范。

错误做法：

```text
匹配成功
↓
等待连线动画
↓
等待爆炸
↓
等待粒子
↓
删除棋子
↓
恢复输入
```

这会使操作非常黏。

正确做法：

```text
匹配成功
↓
逻辑立即标记棋子为 Removed / Resolving
↓
立即更新 Board State
↓
发出 MatchResolved 事件
├── View 播放连线
├── View 播放爆炸
├── Audio 播放声音
├── Haptic 震动
├── Mode 更新进度
└── 输入系统在极短保护窗口后继续接受输入
```

原则：

> 动画不能成为核心逻辑锁。

允许上一组棋子的爆炸动画还未结束时，玩家已经开始操作下一组棋子。

---

## 3.3 配置优先，代码负责规则

以下内容尽量配置化：

- 棋盘大小
- Tile 类型数量
- 时间限制
- 目标
- 提示次数
- 洗牌次数
- FeedbackPreset
- 清洁阶段
- 剧情节点
- 奖励
- 素材映射
- 产品入口

但配置不承担复杂业务逻辑。

不要在 JSON 中创造第二套编程语言。

---

## 3.4 依赖方向必须单向

依赖必须满足：

```text
Content
   ↓
Mode
   ↓
Application
   ↓
Domain
```

表现层和平台层通过接口接入。

Domain 禁止依赖：

```text
Cocos Node
Sprite
AudioSource
Platform API
广告 SDK
微信 API
抖音 API
```

这样规则核心才能独立测试。

---

## 4.2 为什么不优先 Unity

本项目目前主要是：

- 2D
- 轻量
- 小游戏
- 快速迭代
- 快速换皮
- 多平台小游戏发布

因此 V1 没有必要为 Unity 的更重运行时和工程复杂度付出成本。

如果以后产品演化成：

- 重 3D
- 大世界
- 大量 Shader
- 重物理
- Native App 为核心

再重新评估。

---

## 4.3 后端策略

V1：

> 不为了“架构完整”提前建设独立游戏后端。

第一阶段允许：

```text
本地存档
+
平台云能力
+
分析平台
+
平台广告 SDK
```

但所有能力必须通过接口访问：

```text
ISaveService
IAnalyticsService
IAdService
IPlatformService
IRemoteConfigService
```

业务代码禁止直接调用：

```text
wx.xxx()
tt.xxx()
```

以后从微信切抖音、从平台云切独立后端时，不需要修改 Mode 和 Link Core。

# 8. 连线算法设计

## 8.1 V1 规则

默认经典规则：

- 两个 Tile `typeId` 相同
- 两个位置不同
- 路径只能通过空格
- 最多允许 2 次转折
- 可允许路径经过棋盘外一圈

---

## 8.2 推荐算法

V1 使用：

> 带方向状态的 BFS。

搜索状态：

```ts
interface SearchState {
  pos: Position;
  direction: Direction;
  turns: number;
  distance: number;
}
```

约束：

```text
turns <= maxTurns
```

排序优先级：

```text
更少转折
→
更短路径
```

原因：

- 实现稳定
- 容易单测
- 支持以后修改 maxTurns
- 支持障碍物
- 支持特殊 Tile
- 不需要为 0/1/2 折分别维护大量分支

---

## 8.3 棋盘边界

逻辑棋盘建议自动增加一圈虚拟空白：

```text
原始：

A X X X
X X X B

逻辑：

. . . . . .
. A X X X .
. X X X B .
. . . . . .
```

从而自然支持“从棋盘外围绕过去”。

# 9. Board Generator

## 9.1 V1 生成方式

```text
确定 pairCount
↓
生成成对 typeId
↓
随机打乱
↓
填入可用 Cell
↓
检测是否至少存在一个可消除 Pair
↓
如果不存在 → Shuffle
```

V1 不要求生成器保证：

> 从第一步开始存在唯一的、无需洗牌即可完整解完的数学解。

因为这会明显增加实现复杂度。

V1 使用：

```text
DeadlockDetector + Shuffle
```

保证玩家不会被永久卡死。

---

## 9.2 Deadlock

每次 PairRemoved 后：

```text
remaining == 0
→ BoardCleared

remaining > 0
→ hasAvailableMatch()

false
→ DeadlockDetected
→ AutoShuffle
```

# 10. 输入系统

## 10.1 输入流程

```mermaid
stateDiagram-v2

[*] --> Idle

Idle --> OneSelected: select A

OneSelected --> Idle: select A again
OneSelected --> OneSelected: select another invalid choice
OneSelected --> Resolving: select matching B

Resolving --> OneSelected: short guard window ends
Resolving --> Idle: no queued selection

Idle --> Completed: level complete
OneSelected --> Completed: level complete
```

---

## 10.2 快速操作规范

禁止：

```text
为了等完整动画而锁输入 300~800ms
```

建议：

- 逻辑结算立即完成
- 只保留很短的防误触窗口
- 动画并发
- Resolving Tile 不再接收输入
- 其他 Tile 可以尽快继续操作

第一版建议调参起点：

| 参数 | 初始值 |
|---|---:|
| 点击缩放反馈 | 60~90ms |
| 连线出现 | 60~100ms |
| Hit Stop | 30~50ms |
| Break 主动画 | 120~180ms |
| 输入保护窗口 | 50~80ms |
| 屏幕震动 | 40~90ms |

以上不是硬编码标准，必须放入 FeedbackPreset。

# 29. 性能目标

第一阶段基准目标：

| 指标 | 目标 |
|---|---|
| 目标帧率 | 主流设备稳定 60 FPS |
| 游戏过程中长 GC 卡顿 | 不允许明显出现 |
| Tile 高频创建销毁 | 使用对象池 |

| Match Path 计算 | 只在玩家选择第二个 Tile 时执行 |

# 38. Error Handling

错误分三类：

## Recoverable

例如：

```text
广告加载失败
埋点失败
云存档失败
资源重试
```

原则：

> 降级，不中断游戏。

## Gameplay Error

例如：

```text
死局
```

原则：

> 自动恢复，例如 Shuffle。

## Fatal

例如：

```text
LevelConfig 缺失
必要 Bundle 无法加载
```

原则：

> 中止进入关卡 + 明确日志 + Debug 环境快速暴露。

# 40. 安全与合规边界

Core 不保存用户敏感信息。

业务层不要把：

```text
手机号
身份证
真实姓名
```

写入通用 Game Save。

用户身份、支付、广告、隐私授权等必须由平台层 / 业务层独立处理。

任何第三方 SDK：

```text
必须封装到 Infrastructure / Platform
```

禁止在 Domain 和 Mode 中直接散落 SDK 调用。

# 45. 最重要的十条工程约束

1. 三款产品禁止复制 Link Core。
2. Domain 禁止依赖 Cocos。
3. Mode 禁止自己实现连线算法。
4. 动画禁止成为逻辑锁。
5. 清理模式可以慢，输入响应不能慢。
6. 剧情模式关卡不能成为剧情消费障碍。
7. 配置可以描述数据，不创造万能脚本语言。
8. 微信、抖音等平台 API 必须经过 Adapter。
9. 高频 View / Effect 必须优先考虑对象池。
10. “未来可能需要”的能力不进入 V1。

# 47. 开发启动结论

项目不从：

```text
首页
剧情
农场
装修
广告
```

开始。

项目从：

```text
Board
↓
Tile
↓
PathFinder
↓
GameSession
↓
一次成功 Match
↓
一套非常爽的 Feedback Pipeline
```

开始。

第一个需要真正做好的 Demo 应该只有一个目标：

> 玩家连续玩 2~3 分钟纯连连看时，即使没有剧情、没有清理包装、没有复杂成长系统，也能因为点击响应、连线、命中、爆开、音效和 Combo 的连续反馈而觉得“手感很好，想继续点”。

如果这个底层体验成立：

```text
快爽产品
= Link Core + 高密度挑战

清理产品
= Link Core + 清理恢复体验

剧情产品
= Link Core + 低阻力剧情推进
```

三种产品才能真正共享同一套底座，并形成可持续低成本迭代能力。
